# Valhalla 与同类产品详细对比（含持续优化能力）

> 版本：v1.0 · 日期：2026-11-13
> 范围：ValhallaBase / valhalla-server vs Mem0、Zep/Graphiti、Letta、Engram（相邻品类），及全上下文 LM、普通 RAG、LM 微调/LoRA 基线
> 定位一句话：Valhalla 不是又一个“抽取 → 向量/图 → 注入 prompt”的记忆 API，而是**结构可训练的运行时本体**（Triad 会话 + Fate 门控 + 可烘焙权重），LM 只是可选解码头。

---

## 0. 阅读须知：三档证据，禁止混引

业界最常见的错误，是把不同协议、不同语料、不同骨干的数字直接排成一张“排行榜”。本报告把所有数字分成三档，引用时必须带档位：

| 档位 | 含义 | 可比性 |
|---|---|---|
| **A · 同题实测** | 同一批问题、同一骨干（Qwen2.5-3B 行业标定）下多系统实测 | 可横向对比，但样本量小（n=10–30） |
| **B · Valhalla 内部协议** | Valhalla 自有协议（U1–U4、TPI-v2、fate-longchain 等）下的测量 | 证明“该能力存在且可复现”，**不等于**行业基准胜出 |
| **C · 厂商自报** | 各厂商用自有协议/基准公布的数字 | 口径各异，只能作背景，**禁止**与 A/B 档拼表排名 |

硬边界（源自仓库 SSOT 文档，禁止对外宣称）：

- 禁止宣称“在 LoCoMo / LongMemEval 上击败 Mem0”；
- 禁止宣称“RAGTruth 100/100”为当前值（当前：live 38/40、完整缓存 88/100）；
- 禁止宣称“长链 composite 0.95”为当前值（当前 ≈0.882；0.95 是 v1 历史最小集）；
- “留出集 100%”必须同时注明协议 `fate-longchain-unified-v5`、n=3，且与行业 LoCoMo 分开。

## 1. 产品定位与架构对比

| 维度 | ValhallaBase | Mem0 | Zep / Graphiti | Letta（MemGPT） | Engram | 普通 RAG | 全上下文 LM |
|---|---|---|---|---|---|---|---|
| 品类 | 结构运行时本体 | 记忆层 API | 时序知识图谱 | Agent 操作系统/运行时 | 学习型企业记忆层 | 检索管线 | 基线 |
| 核心机制 | Hub/Tile/Stem 三体 + Fate 信号门，语料“孵化”为结构快照 | 抽取事实 → 向量（+可选图）→ 检索注入 | 实体/关系抽取 → 时序 KG（有效期窗口） | 自编辑记忆块（core/archival）+ 工具分页 | 训练出的记忆层，压缩企业知识 | 切块 → 向量检索 → 拼 prompt | 全部历史塞进上下文窗口 |
| 记忆载体 | 结构快照（Triad snapshot）+ 语料索引 | 事实条目（向量库/图） | 图节点/边（带时间有效性） | 文本记忆块 | 模型内/近模型记忆 | 向量索引 | 无（每次全量重发） |
| LM 角色 | 可选解码头，可换骨干；open 类走 native，mcq 走 LM 头 | 负责抽取与作答，和记忆层绑定使用 | 负责作答 | 运行时与模型耦合 | 与训练耦合 | 负责作答 | 本体即作答 |
| 部署形态 | 本地运行时/自托管服务器（本项目 valhalla-server），引擎与权重加密落盘 | 托管 API / 自托管 | 托管 / 自托管（Neo4j 等） | 自托管/云 | 商业 SKU | 自建 | API |
| 多租户/SaaS 成熟度 | 低（研究型运行时） | 高（主打卖点） | 高 | 中 | 高 | 自建 | 高 |

结论：Mem0/Zep/Letta 解决的是“给现有 LLM 应用加一层记忆”；Valhalla 的竞争面不在这一层——它把“会话状态、路由、拒答、持续学习”下沉为结构本身。把两者按同一个 API 维度打分会系统性误判双方。

## 2. 硬指标对比（A 档：同题实测）

协议：`competitor-compare` moderate 集（2026-07-13），骨干锁 Qwen2.5-3B 仅作行业标定。Valhalla 该轮为 hybrid full 配置。

| 基准 | 全上下文 LM | 普通 RAG | **Valhalla** | Mem0（本地语义检索） |
|---|---|---|---|---|
| LoCoMo-15（moderate） | 9/15（60%） | 9/15（60%） | **0/15（0%）** | 5/15（33%） |
| MultiHop-10 | 6/10 | 6/10 | **6/10** | 6/10 |
| LongBench-10 | 2/10 | 2/10 | **1/10** | 2/10 |

行业全量口径补充（不同 n，勿与上表拼行）：`locomo-v1` 全会话（~280+ 行、30 题盲检索）Valhalla 为 **14/30（47%，Tier B）**；厂商自报数字（如 Mem0 的 LongMemEval 宣传值）属 C 档，仓库明确注明“不复现、不引用为对比结论”。

**解读（必须原样保留）**：

1. 在记忆 API 们的主场（LoCoMo 式长对话问答）上，Valhalla 目前是**明确落后**的：同题 0/15 vs RAG 9/15。这不是口径问题，是当前开放问答/证据落地（egress）能力的真实差距。
2. MultiHop 上四家打平，说明差距不在“多跳推理骨架”，而在长会话证据召回与落地的最后一公里。
3. 因此 Valhalla 的可辩护卖点**只能**来自第 3 节的独有协议，不得用 A 档数字做领先宣称。

### 5.3 持续优化结论

1. **“越用越好用”在 Valhalla 身上是被测过的，但形态特殊**：它涨的不是权重，而是结构快照。最硬的证据是污染救援（+38.7pp）和 30 轮课程 96.7%；在干净数据上它只打平冷启动 RAG（87.1%），并不超过传统 LM（100%）。
2. **“多跑轮次就会持续变强”是错的**：cycles 1→8 完全无增益。Valhalla 的持续优化杠杆是**路由质量、定向摄入、快照迁移**，不是堆孵化深度——这与 Mem0 们“多存多检索”也不是一回事。
3. **与梯度路线互补而非替代**：唯一能把持续优化沉淀成权重资产的是 L3 烘焙，但烘焙后问答提升目前**未闭环**（融合仓 MCQ 反而下降）。今天若要“持续优化→模型变强”的硬承诺，LoRA/微调仍是唯一成熟路线；Valhalla 的承诺应限定在“会话层持续变好 + 结构可导出”。
4. **与 Mem0/Zep 的真实分工**：持续优化若指“事实库的增删改与时序治理”，Zep 最强、Mem0 最易用；若指“不改权重让同一会话从污染中自愈并迁移到新会话”，只有 Valhalla 有量化协议。同行在这一点上不是“分数低”，是**没有这个机制**。
5. **缺口（未测）**：无周/月级数据流基准、无大规模遗忘曲线、无 MemoryBench 式流式评测；L2 仅 17 行小语料（n=3）；本服务器尚未在本机复跑 TPI/L2 证明链，仅打通了 L3 生产管线（见 3.3，小样本）。

## 6. 选型建议（按场景）

| 场景 | 首选 | 理由 |
|---|---|---|
| 给现有产品快速加“记住用户” | Mem0 | API 成熟度碾压，Valhalla 不是这一层 |
| 事实随时间变化、需审计“何时为真”（CRM/合规） | Zep/Graphiti | 时序有效期是其核心设计 |
| 长时运行的自编辑 agent | Letta | agent-as-OS 心智最接近 |
| 通用文档问答、快速上线 | 普通 RAG / 全上下文 | A 档同题下准确率与成本最稳妥（LoCoMo 9/15） |
| 多模态同体、主动提醒+拒答、污染自愈、可烘焙自有模型 | **Valhalla** | U1–U4 是其他家没有的机制；但须接受 LoCoMo 式 QA 的当前差距 |
| 要求模型本体持续变强且可回归验证 | LoRA/微调（+ Valhalla L3 观察） | 梯度路线证据链成熟；L3 待 MCQ 闭环后再承诺 |
